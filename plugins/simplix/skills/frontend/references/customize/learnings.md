# Customization Learnings (Staging)

> Staging area for framework- and pattern-level customization learnings that apply to any simplix-react project. Write new entries here with placeholders (`<prefix>`, `<domain>`, `<entity>`, `<EnumType>`) and neutral example vocabulary; fold an entry into the SKILL.md main body once it is stable. A learning specific to one project belongs in that project reference instead — see SKILL.md § Learnings from Trial and Error.

1. **`DetailBadgeField` looks its tone up by the RAW `value`, so a boot enum must be resolved before it is passed.** Its body is `variants[value] ?? "default"` — hand it the boot-enum object the DTO carries and every lookup misses, so the badge renders `default` no matter what the variant map says, while `displayValue` still shows the right label. The failure is silent and looks like a broken tone map. Pass `value={resolveBootEnum(x) ?? ""}` alongside `displayValue={enumLabel("<EnumType>", resolveBootEnum(x) ?? "")}`. The scaffold emits the unresolved form (`value={displayData.<field>}`), so every generated detail needs this fixed at customization time.

2. **Soft-delete system fields never reach a user-facing surface — delete them from the scaffold output.** A SimpliX-backed entity carries `deleted` and `deletedTimestamp`; the scaffold turns both into a list column, a `cardContent` row, and a detail field. They say nothing: a soft-deleted row is filtered out of the list, so the flag always reads false and the stamp always reads `-1`. Strip them from the column set, the `cardContent` block, the detail section, the form, and the filter set, then clean up the imports left unused. The framework has no declarative "hidden by default" — `hiddenColumns` is a runtime toggle the operator opens — so hiding means removing from source. Same treatment for the entity PK and the audit quartet (`createdAt`/`createdBy`/`updatedAt`/`updatedBy`): `CrudDetail`'s `auditData` slot already carries them.

3. **A nullable enum in a detail row uses `DetailFields.DetailBadgeField`, never a bare badge inside `DetailFieldWrapper`.** Module badge shells (`StatusBadge`/`EnumBadge` wrappers over `resolveBootEnum`) return `null` for an absent value — correct in list cells and inline flex rows, but inside a `DetailFieldWrapper` it leaves a silently blank row while sibling `DetailFields.*` rows show the shared no-value badge. For a detail/dialog row whose enum can legitimately be absent (e.g. a match/verdict field that only exists when something matched), render it with `DetailBadgeField` (`value={resolveBootEnum(x) || null}` + `displayValue` + the module's variant map) so the empty state goes through the shared fallback. Mandatory-valued enum rows may keep the wrapper+badge shape.

4. **A message that tells the reader to reach a contact is written twice, and the pair is chosen by whether the contact is actually rendered.** Deployment-configured addresses (a sales address, a support address, an operator's escalation path) are optional fields on a settings read, and the chrome that displays them hides them when they are absent. A single message saying "get in touch" then leaves the reader instructed to do something the page gives them no way to do — worst on a public surface, where they have no other channel. Write both variants (`<key>` and `<key>NoContact`), pick between them in ONE shared hook that owns the read (`useContactText(withContact, withoutContact, params)`), and route every such message through it. A codebase that already gates one message this way and not the next two has the defect, not the convention: the check when writing any such string is "does this page render the address it just told them to use".

5. **A shared catalogue is edited surgically; a whole-file write is preceded by a fresh read.** Locale catalogues (`modules/<domain>/src/locales/**/*.json`) and codegen output are appended to by many tasks that do not otherwise touch the same files, so the hazard is not two writers at the same moment — it is ONE writer that reads the file early, works for a while, and writes the whole file late. Everything added in between is silently gone: the keys vanish, the widgets that name them stay, and the screens print `<namespace>.<key>` where the sentence should be. Nothing errors, and git shows a plausible small diff because the lost keys were never committed. Edit these files key by key. When a whole-file write is genuinely needed (a scripted bulk edit, a sort, a reformat), re-read the file inside the same step that writes it, never from a copy read earlier in the task. The audit's `missing-translation-key` rule is what catches the loss afterwards — treat a sudden crop of that error across files you did not touch as this, not as somebody forgetting their keys.

6. **A client-generated idempotency key is scoped to the payload it guards, never to the screen or the record it was reached from.** The point of the key is that a repeated submission of the SAME request returns the first answer; a key scoped to something coarser (the plan, the entity, the tab) survives the user going back and CHANGING the form, so the server answers the new basket with the old record and the screen after the submit shows values nobody typed — a silent cross-screen disagreement no test catches, because both screens are individually correct. Derive the stored key from the submitted values themselves, keep it under a scope string built from them, and release it once the record it wrote can no longer move (paid, closed, cancelled) so a second identical purchase is a second record. The release half is the one that gets written and never wired: a `clearX`-style helper with no importer means the flow does not have it.
