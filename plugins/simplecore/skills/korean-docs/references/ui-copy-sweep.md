# 전수 검토 절차 (화면 문구·문서 공통)

한국어 산출물을 전수로 검토하고 고치는 작업의 절차. 무엇이 어색한지를 판정하는 기준은
[ui-copy.md](ui-copy.md)에 있고, 이 파일은 **그 기준을 어떤 순서로 적용하는가**를 정한다.

**적용 대상**: 화면 문구(i18n 자원·메시지 번들·메일 템플릿·화면 스크립트, 프로젝트
`.claude/l10n.json`에서 `register: "screen"`인 부류)와 **문서**(설계·기술 문서, README, 매뉴얼,
계획서). 절차는 같고 **단위만 다르다** — 화면 문구는 화면 하나, 문서는 문서 하나가 8단계의 단위다.

**문서를 검토할 때 달라지는 것은 8단계뿐이다.** 화면 맥락 검토(8-1~8-6)는 제목·경고·버튼·목록처럼
화면에만 있는 자리를 대조하므로, 문서에서는 그 자리를 문서의 것으로 바꿔 읽는다 — 제목과 첫 문단이
같은 것을 말하는가, 절 제목과 그 절의 내용이 맞는가, 표의 머리글이 그 열의 값을 이름하는가, 같은
개념이 문서 전체에서 한 이름인가. **나머지 단계는 그대로다.**
---

# 절차

## 0. 검색으로 시작하지 않는다

**일부 예문만 검색해 고치고 끝내지 않는다.** 검색은 눈으로 읽어 발견한 패턴을 넓힐 때 쓰는 보조
수단이다. 검색 결과만 고치면 목록에 없던 같은 종류가 그대로 남고, 남은 것은 고쳐진 문장들 사이에서
정상으로 읽힌다. **모든 파일과 모든 문장을 파일 이름순으로 읽는다.**

## 1. 프로젝트 규칙과 용어를 먼저 확인한다

1. 현재 경로와 상위 경로에 적용되는 지시 파일(`AGENTS.md`·`CLAUDE.md`)
2. 프로젝트 용어사전과 표기 규칙(`.claude/GLOSSARY.md`)과 규칙 팩(`.claude/l10n-rules.json`)
3. 프로젝트가 정한 빌드·검사 명령
4. 이미 수정된 파일과 사용자가 작업 중인 변경 사항

**기존 변경 사항을 되돌리거나 덮어쓰지 않는다.** 법정 용어·기술 용어가 의심스러우면 임의로 바꾸지
말고 용어사전과 같은 화면군의 사용례를 먼저 확인한다.

## 2. 검토 대상 목록을 확정한다

화면 파일을 이름순으로 정렬하고 전체 개수를 센다. 시작 전에 전체 파일 수와 구역 범위를 파악해야
끝에서 누락을 확인할 수 있다. **검색 결과에 나온 파일만 검토하지 않는다** — 첫 구역의 첫 파일부터
마지막 구역의 마지막 파일까지 순서대로 읽는다.

## 3. 모든 표시 문구를 순차 검토한다

각 파일에서 사용자에게 보일 수 있는 문구를 전부 읽는다.

- 화면 제목과 부제
- 메뉴·탭·경로 표시·구역 제목
- 필드 라벨·단위·선택 항목
- 버튼과 행 작업 메뉴
- 안내문·도움말·툴팁
- 확인 창과 경고 문구
- 빈 상태·오류 상태·로딩 상태
- 표 머리글·상태 배지·요약 카드
- 예시 데이터와 활동 이력
- 접근성 라벨
- 화면 설명으로 노출되는 메모

코드 식별자·함수명·CSS 클래스명처럼 사용자에게 보이지 않는 값은 대상이 아니다. **다만 화면 문자열을
식별자로도 쓰는 구조라면 참조 관계를 확인하고 고친다** — 문구만 바꾸면 동작이 깨진다.

**27,830개를 그냥 읽을 수는 없다 — 렌즈로 줄인 뒤 읽는다.**
[reading-lens.md](reading-lens.md)의 넓은 패턴이 비유가 있을 만한 문장만 뽑아 준다(이 규모에서
1,336개). 렌즈에 걸린 것을 **파일명 순서로** 읽어 판정하고, 그다음에 렌즈에 걸리지 않은 것을 훑는다.
**렌즈를 검사로 착각하지 않는다** — 렌즈도 어간 목록이라 계열 자체를 모르면 못 잡으므로, 마지막
그물은 여전히 전부 읽는 것이다.

문장마다 열 가지로 판정한다.

1. 처음 읽는 사람이 한 번에 뜻을 아는가
2. 업무용 소프트웨어에서 실제로 쓸 법한 표현인가
3. 영어 원문을 떠올려야 이해되는 문장은 아닌가
4. 사물이나 화면이 사람처럼 행동하고 있지 않은가
5. 비유형 동사를 더 정확한 기능 동사로 바꿀 수 있는가
6. 주체·대상·조건·결과가 분명한가
7. 법적·기술적 의미가 원문과 같은가
8. 같은 개념을 다른 화면에서도 같은 용어로 쓰는가
9. 조사·어순·서술어 호응이 자연스러운가
10. 제목과 설명이 같은 사실을 말하는가

## 4. 문장 단위로 다시 쓴다

문제가 있는 문장은 **단어 하나만 치환하지 않는다.** 순서대로 다시 쓴다.

1. 원문이 전달하려는 사실을 한 문장으로 정리한다
2. 실제 행위 주체와 동작을 확인한다
3. 비유와 추상 명사를 지운다
4. 사용자가 알아야 하는 조건이나 결과를 앞에 둔다
5. 가장 구체적인 서술어를 고른다
6. 그 화면의 기존 문체와 높임 수준에 맞춘다
7. 소리 내어 읽는다고 가정하고 어색한 호흡을 다듬는다

**짧게 만드는 것 자체는 목표가 아니다.** 짧지만 뜻이 모호한 문장보다, 필요한 관계를 정확히 설명하는
자연스러운 문장이 낫다.

**고쳐 쓴 문장을 규칙에 다시 통과시킨다.** 대신 넣은 말이 그 자체로 금지 표현인 사고가 이 작업에서
가장 자주 난다 — 「목록에 딸린 미리 보기」로 고쳤더니 `attached-to-for-belong`에 걸렸고, 용어사전의
대체 열 일곱 자리가 그 자체로 비유였다. 고친 파일을 `check`와 `rules`에 다시 넣기 전에는 그 자리를
끝난 것으로 세지 않는다.

## 5. 반복 패턴을 넓혀 다시 찾는다

순차 검토를 마친 **뒤에** 전체 검색을 보조 수단으로 쓴다. 한 문장에서 발견한 어간의 활용형을 넓게
검색한다 — 기대다·기댄다·기대는·기대지 / 걸리다·걸린다·걸리는·걸리지 / 싣다·싣는다·실어 /
막히다·막는다·막힌 / 열리다·열린다·열리는 / 무너지다·무너진다 / 살아나다·되살아난다 / 오르다·
올라간다·올라온다 / 밀리다·밀린다 / 가르다·갈린다 / 뒤에 있다·위에 서다.

검색된 표현이 실제 물리 동작인지, 정식 기술 용어인지, 비유인지 문맥마다 판단한다. **정규식이나 일괄
치환만으로 작업을 끝내지 않는다.** 일괄 치환을 썼다면 바뀐 문장을 전부 다시 읽어 조사와 의미를
확인한다.

## 6. 화면군끼리 용어를 통일한다

같은 기능을 다루는 목록·상세·등록·도움말·모바일·태블릿 화면을 함께 놓고 비교한다.

- 같은 상태에 다른 이름을 쓰지 않는지
- 목록의 열 이름과 상세 화면의 필드명이 일치하는지
- 도움말 제목과 실제 화면 제목이 일치하는지
- 데스크톱과 태블릿의 작업명이 일치하는지
- 법적 의무의 명칭과 순서가 일치하는지
- 적용·등록·배정·지정·선임처럼 뜻이 다른 동사를 섞어 쓰지 않는지

### 한 동작에 이름이 둘이면 규칙도 렌즈도 못 본다

**낱말 하나만 보면 셋 다 옳다.** 「연결」도 「잇기」도 「붙이기」도 정상적인 한국어라 규칙이 잡을
근거가 없고, 렌즈에 걸려도 읽는 사람이 그 자리에서는 어색함을 못 느낀다. **잘못은 낱말이 아니라
낱말들 사이에 있다** — 한 제품이 같은 동작을 세 이름으로 부르는 것.

그래서 이 단계는 읽기가 아니라 **세기**로 한다. 동작 하나를 정하고 후보 이름을 모두 세어, 가장
많이 쓰인 것으로 통일하고 나머지를 그 자리에서 바꾼다.

```bash
for w in 연결 잇기 붙이기 매핑; do printf '%-8s %s\n' "$w" "$(grep -ro "$w" <대상> | wc -l)"; done
```

**한 파일 안에서 동작과 그 반대가 다른 어근을 쓰면 그것이 가장 확실한 신호다** — 「잇기」 옆에
「연결 끊기」가 있으면 이름이 갈린 것이 이미 증명된 셈이다.

같은 방식으로 세어야 드러나는 자리가 셋 더 있다.

- **설명을 여는 것과 열리는 것의 제목** — 카드 제목과 그 카드가 여는 다이얼로그 제목이 다르면
  누른 사람이 다른 곳에 왔다고 느낀다. 열두 카드가 같고 하나만 다른 식으로 어긋난다.
- **본문의 수와 지표의 수** — 「다섯 부처의 법이 겹친다」고 적고 타일에는 「6개 부처」라고 적은 자리.
  둘 다 문장으로는 옳아서 읽기로도 잘 안 잡히고, 나란히 놓고 세어야 드러난다.
- **한 술어가 덮는 주어가 둘일 때** — 「톨루엔과 소음은 이 사람이 실제로 마신 양이 아니다」에서
  소음은 마실 수 없다. 주어가 둘 이상인 문장은 술어를 각 주어에 따로 붙여 읽는다.

### 목소리가 둘이면 두 방향을 다 검사한다

**한 파일이 두 목소리를 담는 산출물이 있다** — 화면 문구는 제품이 사용자에게 말하는 합니다체이고,
같은 파일의 주석·노트·설명은 만드는 쪽이 읽는 쪽에게 말하는 -다체다. 매뉴얼과 그 안의 화면 인용,
릴리스 노트와 그 안의 메시지도 같은 구조다.

**그런 프로젝트의 검사는 거의 언제나 한 방향만 있다.** 「화면 문구가 -다체로 새지 않았는가」는
있고 「설명이 합니다체로 새지 않았는가」는 없다. 한쪽만 지키면 반대쪽은 소리 없이 어긋나고, 그
상태가 검사 화면에서는 통과와 구별되지 않는다 — 실제로 그렇게 63개 파일에 111자리가 쌓였다.

- **규칙 팩으로는 판정할 수 없다.** 어느 목소리인지는 마크업이나 필드 이름이 정하는데, 규칙의
  읽개는 마크업을 벗겨 낸 문자열만 본다. **그 프로젝트의 빌드 검사에 넣는다.**
- **양쪽 예문을 다 넣는다** — 새는 꼴 하나, 정상인 꼴 하나. 그리고 **인용은 제 목소리를 지킨다**:
  설명 안에 화면 문구를 「」로 옮겨 적은 것은 합니다체가 맞으므로 검사에서 뺀다.

### 종결형을 찾는 정규식은 마침표에 걸지 않는다

**「…표시합니다.」만 찾으면 「…표시합니다({{ref}}).」와 「…표시합니다<br>」가 통째로 빠져나간다.**
111자리 가운데 36자리가 이 구멍으로 첫 훑기를 지났고, 같은 실수를 표어형 단정문 규칙이 `$`
앵커에서 이미 한 번 냈다.

**종결형은 절을 닫는 것 전부에 건다**: 마침표, 여는 괄호, 여는 태그, 문자열을 닫는 따옴표, 줄 끝.

```
(합니다|습니다|입니다|하세요|십시오)(?=[.。(<'`]|\s*$)
```

**규칙을 쓰고 나면 「깨끗한 꼴」이 아니라 「새는 꼴」로 먼저 시험한다** — 참조로 끝나는 문장, 태그로
끝나는 문장, 줄 끝에서 끝나는 문장을 각각 넣어 셋 다 잡히는지 본다.

## 7. 문법을 전체 범위에서 다시 검사한다

수정한 파일만이 아니라 검토 대상 전체를 다시 훑는다.

- 잘못된 조사
- 어색한 관형절
- 주어와 서술어 불일치, 목적어와 서술어 불일치
- 중복 단어와 이중 표현
- 불필요한 피동과 이중 부정
- 두 칸 이상의 공백
- 문장 종결 방식 불일치
- 제목과 본문의 명칭 불일치
- 기계적 치환이 남긴 문장 조각
- 높임말과 해라체가 한 화면에 섞인 곳
- 「할 수 있습니다」와 「가능합니다」의 중복
- 괄호 앞뒤, 숫자와 단위의 띄어쓰기 불일치

조사 어긋남과 같은 말의 연속은 감사 스크립트가 잡는다 — 사람은 나머지를 본다.

## 8. 화면 맥락 2차 검토

문장 단위 검토를 마친 뒤 각 화면의 문구를 **표시 순서와 기능 관계에 따라** 다시 읽는다. 브라우저로
보는 시각 검토와는 별개의 단계이며, 소스에 선언된 제목·설명·상태·경고·필드·버튼·패널·도움말을
순서대로 대조해 수행할 수 있다.

**처음 적용할 때는 대표 화면에 먼저 시범 적용한다** — 역할·기기·화면 구조가 서로 다른 것들로
고른다: 데스크톱 목록과 상세 패널 / 등록·수정 폼 / 승인·결재 화면 / 경고와 차단 상태가 있는 화면 /
모바일 화면 / 태블릿 현장 입력 화면 / 관리자 설정 화면 / 법정 의무와 증빙을 다루는 화면. 시범
적용에서 문장이 불필요하게 길어지는지, 법적 의미가 달라지는지, 화면마다 같은 내용을 반복하게 되는지
확인한다. **검증된 규칙과 실제 수정 사례만 이 파일에 더한 뒤 전체에 적용한다.**

### 8-1. 제목부터 작업 버튼까지 한 흐름으로 읽는다

1. 화면명과 설명이 같은 기능을 말하는가
2. 상태명과 요약 수치가 화면 설명의 핵심 대상을 집계하는가
3. 경고가 이 화면에 실제로 있는 문제를 설명하는가
4. 경고가 요구한 조치를 수행할 버튼이나 이동 경로가 있는가
5. 버튼명이 안내문의 동작명과 같은 말인가

경고가 「교육 과정을 개설하세요」인데 버튼이 「회차 열기」이면 둘 다 **「교육 과정 개설」**로
통일한다.

### 8-2. 경고와 확인 문구의 정보 구조

경고는 되도록 **문제 → 원인 → 영향 → 조치** 순서로 준다: 지금 어떤 상태인가 · 어떤 조건을 충족하지
않았는가 · 어떤 작업을 할 수 없는가 · 누가 무엇을 해야 하는가. 모든 경고를 네 문장으로 늘리라는 뜻은
아니고 화면에서 이미 분명한 것은 반복하지 않는다. 다만 **제한 사실만 말하고 해결 방법을 빼거나,
조치만 말하고 원인을 감추지 않는다.**

확인 창은 다섯 가지를 확인한다 — 실행할 동작의 정확한 이름 · 영향받는 대상과 개수 · 실행 후 유지되는
정보와 바뀌는 정보 · 되돌릴 수 있는지 · 되돌린다면 그 단위.

### 8-3. 목록과 상세 패널의 대상 일치

- 목록에서 고른 대상과 상세 패널의 주어가 같은지
- 목록 열 이름과 상세 필드명이 같은 개념에 같은 용어를 쓰는지
- 목록의 상태와 상세 패널의 설명이 모순되지 않는지
- 상세 패널의 작업 버튼이 고른 대상에 하는 동작인지
- **빈 상태나 미선택 상태에 특정 레코드를 가리키는 문장이 남아 있지 않은지**

### 8-4. 화면 간 절차와 용어 일치

목록·상세·등록·확인 창·도움말·모바일·태블릿 대응 화면을 화면군으로 묶어 대조한다 — 앞 화면의
버튼명과 다음 화면의 제목 / 요청 화면의 동작명과 이력 화면의 사건명 / 정책 화면의 상태명과 판정
화면의 상태명 / 경고의 해결 방법과 실제 수정 화면의 버튼명 / 데스크톱과 모바일에서 같은 작업을 부르는
이름.

**화면 전환을 물리적 이동 비유로 설명하지 않는다** — 「여기서 연다」·「다음으로 넘어간다」가 아니라
「상세 화면으로 이동한다」·「승인 완료 후 신청서를 작성할 수 있다」처럼 대상과 결과를 밝힌다.

버튼도 「열기」·「올리기」·「잡기」·「빼기」·「넣기」로 업무 동작을 대신하지 않고, 누른 뒤 실제로 하는
일을 이름으로 쓴다 — 재평가 열기 → 재평가 / 검사 일정 잡기 → 검사 신청 / 조건부 통과 올리기 →
조건부 통과 요청 / 원장에서 빼기 → 원장 항목 제외 / 증빙 올리기 → 증빙 등록. 실제 출입문 열기·파일
열기처럼 열림 자체가 기능이면 그대로 둔다.

**화면 이동 버튼은 목적지 이름을, 처리 버튼은 수행 동작을 쓴다.**

### 8-5. 역할별 정보 우선순위

문장의 정확성뿐 아니라 **현재 역할이 조치할 수 있는 정보를 먼저 준다.** 역할마다 먼저 알아야 하는
것이 다르다 — 실무자는 지금 할 일·기한·제한 사유·문의 방법, 담당 관리자는 판정 근거·미충족 요건·영향
대상·후속 조치, 승인자는 승인 조건·미확인 항목·승인 후 영향 범위, 시스템 관리자는 설정값·적용 범위·
변경 영향·복구 방법, 외부 조직 사용자는 직접 처리할 수 있는 작업과 상대 조직에 요청해야 하는 작업.

**현재 역할이 수행할 수 없는 작업을 명령형으로 안내하지 않는다** — 외부 조직 화면의 「교육 회차를
개설하세요」는 「상위 조직에 교육 과정 개설을 요청하세요」다.

### 8-7. 한 문장에 핵심 관계 하나

상태·원인·법적 근거·영향·조치를 한 문장에 모두 잇지 않는다. 주체가 바뀌는 지점 · 시간 조건이 바뀌는
지점 · 상태 설명에서 사용자 조치로 넘어가는 지점 · 근거 설명에서 시스템 처리로 넘어가는 지점에서
나눈다. 나눈 뒤 같은 명사가 반복돼 어색하면 두 문장의 주어를 조정한다.

### 8-8. 비시각적 길이·중복 검사

브라우저를 쓰지 않아도 소스에서 확인한다 — 버튼 하나에 원인과 결과를 함께 넣지 않았는지 · 탭과
배지가 문장으로 길어지지 않았는지 · 표 머리글이 설명처럼 장황하지 않은지 · 같은 경고가 제목·본문·
도움말에 세 번 반복되지 않는지 · 모바일 본문이 데스크톱 설명을 그대로 복사해 길어지지 않았는지.

**시각적 줄바꿈·실제 잘림·화면 밀도는 렌더링 결과를 보지 않고 확정하지 않는다.** 사용자가 시각
검토를 제외하도록 요청했다면 그 제한을 최종 보고에 적되, 위의 비시각적 검사는 수행한다.

### 8-9. 맥락 검토 완료 판정

- 화면 설명만 읽어도 화면의 목적을 안다
- 현재 상태와 제한 사유가 구분된다
- 사용자가 다음에 할 수 있는 작업을 안다
- 안내문과 실제 버튼이 같은 동작명을 쓴다
- 목록·상세·확인 창·이력이 같은 대상명을 쓴다
- 현재 역할에 없는 권한을 수행하라고 안내하지 않는다
- 업무 절차와 시스템 처리의 선후 관계가 분명하다
- 자연스럽게 고친 결과가 불필요하게 장황해지지 않았다

### 8-10. 무작위 표본으로 검수 누락을 확인한다

파일명 순서대로 전수 검토하고 반복 패턴 검색을 마친 **뒤에**, 전체 화면 파일에서 15~20개를
무작위로 다시 골라 **처음 검토하는 파일처럼 읽는다.** 이미 수정했다는 기억이나 검색 결과에
의존하지 않고, 각 문장을 표시 순서대로 읽어 자연스러운 한국어인지 다시 판정한다.

표본에는 본문이 긴 기본 화면뿐 아니라 다음이 들어가게 한다.

- 다이얼로그·도움말 상태만 정의하는 짧은 래퍼 파일
- 기본 화면을 가져와 이름·상태·메모만 덮어쓰는 파일
- 태블릿·모바일 대응 화면
- 오류·빈 상태·권한 제한 상태
- 법정 용어와 기술 용어가 함께 쓰인 화면

**래퍼 파일은 본문이 짧다는 이유로 빼지 않는다.** 가져온 기본 화면의 문구가 자연스러워도 래퍼가
질문형 화면명, 번역체 상태명, 압축된 노트를 다시 얹을 수 있다. 화면 이름·상태·폼·목록·언어 설정·
메모를 각각 확인하고, 실제 사용자 화면에 나가는 값인지 구분한다.

표본에서 새 문제가 하나라도 나오면 다섯 단계로 처리한다.

1. 그 파일의 문제 문장을 고친다
2. 같은 어간과 문장 구조를 전체 파일에서 다시 검색한다 — **표본에서 찾은 것은 그 파일만의 문제인
   적이 거의 없다**
3. 기존 규칙으로 설명되지 않으면 판정 기준에 규칙을 더한다
4. 새 규칙을 이미 검토한 파일에도 적용한다
5. **다른 표본을 새로 뽑아 다시 읽는다**

**한 번 뽑아 보고 끝내지 않는다. 새 문제가 하나도 나오지 않는 표본이 나올 때까지 뽑기를
되풀이한다.** 표본에서 무언가 나왔다는 것은 전수 검토가 그 부류를 통째로 지나쳤다는 뜻이고, 그
부류가 하나뿐이라고 볼 근거가 없다. 회차마다 앞 회차와 겹치지 않게 뽑고, 몇 회를 돌았고 각 회차에서
무엇이 나왔는지를 세어 둔다 — **그 수열이 0으로 끝나야 검수가 끝난다.**

**세 회차 넘게 계속 새 문제가 나오면 뽑기를 더 하기 전에 멈춘다.** 전수 검토 자체가 한 단계를
건너뛴 것이므로, 표본이 아니라 그 단계를 다시 돈다.

**멈추지 않으면 스무 회차를 돌고도 수렴하지 않는다.** 표본은 회차마다 다른 비유 계열을 하나씩
집어 올리는데(기한을 시계라 부르는 것, 담당자를 주인이라 부르는 것, 단계를 걸음이라 부르는 것…),
그때마다 그 한 건만 고치면 같은 계열의 나머지가 다음 회차에 다시 나온다. 회차가 줄지 않는 것은
표본이 부족해서가 아니라 **계열을 전수로 훑지 않아서다.**

그래서 세 회차째부터는 뽑기를 멈추고 이렇게 한다.

1. 그때까지 표본이 찾아낸 비유 낱말을 **한 목록으로 모은다**
2. 그 목록 전체를 저장소에 한 번에 훑는다 — 낱말마다 정상 쓰임을 제외 패턴으로 함께 적는다
   (「자리」는 자릿수와 좌석을, 「품」은 제품·작품을, 「시계」는 시계열을 끌어온다)
3. 후보를 문맥으로 판정해 고친다 — **대부분은 정상 한국어이고, 실제 위반은 이름 자리에 몰려 있다**
4. 훑기를 마친 뒤에 표본을 다시 뽑아 수렴을 확인한다

**표본이 계속 찾아내는 것이 규칙에 없다면 그것이 진짜 결과다.** 회차마다 고치기만 하고 규칙 팩과
판정 기준에 올리지 않으면, 다음 제품에서 같은 계열을 처음부터 다시 찾게 된다.

무작위 표본 검수는 전수 검토를 대신하지 않는다. 정규식으로 찾기 어려운 의인화, 표어형 단정문,
문맥에 따라 달라지는 비유형 동사, 짧은 래퍼 파일의 문구를 찾아내는 **최종 누락 검사**다.


## 9. 검사와 빌드

프로젝트가 정한 검사 명령을 실행한다. 최소한 다음을 수행한다.

1. 변경한 파일의 문법 검사(모듈 파싱·타입 검사 등 그 프로젝트의 방식)
2. 프로젝트의 게이트 검사
3. 산출물 재생성(보드·번들 등 생성물이 있으면)
4. 변경분의 공백·충돌 표식 검사
5. 감사 스크립트 — **네 명령을 다 돌린 뒤에 판정한다**

```bash
T="$HOME/.claude/skills/simplecore/skills/korean-docs/scripts/l10n.mjs"
node "$T" check [경로...]        # 낱말 금지·조사
node "$T" rules                  # 문장 규칙 훑기
node "$T" audit                  # 자원 감사
node "$T" suspects               # 문체 의심 문장
```

`check` 하나만 0건인 것은 통과가 아니다. **새로 만든 파일은 감사 전에 스테이징한다** — 열거가
`git ls-files`로 이루어져 추적되지 않은 파일은 조용히 빠지고, 그 침묵이 「문제 없음」으로 읽힌다.

검사 실패가 문구 수정 때문이면 원인을 찾아 고친다. 시각 검토를 제외하도록 요청받았으면 브라우저를
실행하지 않고, 최종 보고에 그 사실을 분명히 적는다.

## 작업 중 새 패턴을 찾으면 그 자리에서 규칙으로 만든다

**이 파일은 고정된 체크리스트가 아니라 검토 결과를 반영하는 작업 기준서다.** 기존 항목으로 설명되지
않는 어색한 문장 구조를 만나면 원문을 고치는 것과 **같은 변경에서** 항목을 더한다. 작업이 끝난 뒤
기억에 의존해 한꺼번에 추가하지 않는다.

새 항목에는 일곱 가지를 담는다.

1. 문제가 되는 문장 구조와 활용형
2. 일반적인 한국어 사용자에게 어색한 이유
3. 비유·직역·의인화·모호성 중 어느 유형인지
4. 실제 기능을 확인할 때 물어야 할 질문
5. 수정 전·후 예시
6. 정상적인 사용까지 잘못 고치지 않기 위한 예외
7. 전체 파일에서 같은 패턴을 다시 찾을 검색 관점

기계로 판정되는 것이면 같은 변경에서 규칙 팩(`RULES.base.json` 또는 프로젝트
`.claude/l10n-rules.json`)에 hit/miss 예문과 함께 등재하고, 낱말 금지는 용어사전에 넣는다.
**규칙을 더한 뒤에는 이미 검토한 파일을 그 패턴으로 다시 훑는다** — 문서만 갱신하고 앞의 파일을 다시
보지 않으면 지나온 자리에 같은 문장이 남는다.
