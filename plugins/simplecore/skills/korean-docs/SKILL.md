# 한국어 산출물 기준 (답변·문서·번역·교정)

모든 프로젝트의 모든 한국어 산출물 — 답변부터 문서까지 — 에 적용하는 범용 스킬. 프로젝트별 용어사전으로 용어 일관성을, 문체 레퍼런스로 자연스러운 한국어를 보장한다. 용어사전은 쓸수록 진화한다 — 작업 중 내린 용어 결정을 즉시 등재해 다음 작업의 표준으로 만든다.

## 적용 범위 — 두 가지 모드

**답변 모드** (모든 한국어 답변·설명·간단한 산출물) — 별도 워크플로 없이 다음만 적용한다:

- [references/response-style.md](references/response-style.md)의 상시 기준(문장 원칙·어휘·표기·말투)을 따른다. **지금 이 맥락에 그 내용이 없으면 읽는다** — 아래 "읽었다는 기억은 읽은 것이 아니다"를 본다.
- 프로젝트에 용어사전(`.claude/GLOSSARY.md` 또는 루트 `GLOSSARY.md`)이 있으면 그 표준 번역·금지 표기를 답변에도 적용한다.
- 용어사전 생성 제안과 감사 실행은 하지 않는다 — 문서 작업 모드에서만 한다.

**문서 작업 모드** (문서 작성·번역·교정·검수·용어사전 관리) — 아래 시작 절차부터 전체 워크플로를 따른다.

## 읽었다는 기억은 읽은 것이 아니다

기준은 **지금 맥락에 실려 있을 때만** 적용된다. "세션당 한 번 읽는다"는 세션이 처음부터 끝까지 한 맥락일 때만 성립하고, 긴 세션에서는 성립하지 않는다.

대화가 길어지면 앞부분이 요약으로 접힌다. 그때 남는 것은 **"이 스킬을 호출했다"는 표시뿐이고, 기준의 내용은 사라진다.** 그 상태에서 "이미 읽었다"고 판단하면, 아무 기준도 없이 한국어를 쓰면서 기준을 지키고 있다고 믿게 된다 — 침묵하는 실패라서 산출물이 나온 뒤에야, 그것도 사람이 어색함을 느꼈을 때만 드러난다.

**판정은 기억이 아니라 맥락으로 한다.** 한국어를 쓰기 직전에 자문한다: 금지 패턴 표를, 어휘 대체 목록을, 표기법 항목을 **지금 인용할 수 있는가.** 하나라도 막히면 읽지 않은 것이다. 다시 읽는 비용은 파일 하나이고, 건너뛴 대가는 다시 써야 하는 산출물이다.

같은 것이 프로젝트 용어사전에도 적용된다. 요약 뒤에 이어지는 작업은 용어사전을 다시 읽고 시작한다.

## 구성 요소

| 파일 | 용도 |
| ---- | ---- |
| `GLOSSARY.base.md` | 기본 용어사전. 프로젝트와 무관한 표기·번역투 규칙. 감사 시 항상 함께 적용 |
| `RULES.base.json` | 기본 문장 규칙 팩. hit/miss 예문을 실은 정규식 규칙이며 `rules` 훑기가 쓴다. `universal` 스코프는 항상, 도메인 스코프(`saas` 등)는 프로젝트가 `.claude/l10n.json`의 `ruleScopes`로 켤 때 적용 |
| `scripts/l10n.mjs` | 통합 CLI. `check`(문서 감사) · `audit`(다국어 자원 감사) · `rules`(문장 규칙 훑기·`--test` 검증) · `suspects`(문체 의심 문장) · `grep`·`list`·`stats` · `apply`(다시 쓴 문장 반영) |
| `scripts/check-glossary.mjs` | 문서 감사의 훅 진입점. `l10n.mjs check`와 같은 엔진(`scripts/lib/`)을 쓰므로 판정이 같다 — 쓰기 시점 훅이 이 경로를 실행한다 |
| `templates/GLOSSARY.md` | 프로젝트 용어사전 템플릿 (`check --init`으로 생성) |
| `references/response-style.md` | 상시 적용 기준 — 문장 원칙·금지 패턴·어휘 대체 목록·표기법·말투·금융/퀀트 도메인 용어. 어휘·표기의 원본 (전역 CLAUDE.md가 필수 참조) |
| `references/korean-style.md` | 심각도(S1/S2)별 번역투·AI 문체 패턴 카탈로그 + 번역 문체·원문 충실도 기준 (교정·검수용) |
| `references/ui-copy.md` | 문장 판정 기준 — 비유·의인화·표어형 단정·추상어 압축·질문형 이름·업무 은어의 관점 A~W. **화면 문구와 문서 공통**이며 화면 전용 절에는 그 표시가 붙어 있다 |
| `references/ui-copy-sweep.md` | 전수 검토 절차 — 읽는 순서, 맥락 2차 검토, 무작위 표본, 완료 판정과 보고 (화면 문구든 문서든 통째로 검토·수정할 때) |
| `references/reading-lens.md` · `references/lens.txt` | **읽기 렌즈** — 규칙이 좁아 놓치는 것을 사람이 읽을 양으로 줄이는 넓은 패턴. `grep --regex "$(cat …/lens.txt)"`로 쓴다 |

## 시작 절차 (문서 작업 공통)

1. **프로젝트 용어사전을 찾는다.** 현재 디렉터리에서 위로 올라가며 각 디렉터리의 `.claude/GLOSSARY.md`(기본 위치) → `GLOSSARY.md` 순서로 확인한다. 감사 스크립트도 같은 방식으로 탐색하며, `.git`이 있는 디렉터리(프로젝트 경계)나 홈 디렉터리에서 멈춘다. 두 위치에 모두 있으면 `.claude/GLOSSARY.md`가 우선하고 루트 파일은 무시되므로 한 곳에만 둔다.
2. **찾았으면 처음부터 끝까지 읽는다.** 세션마다 다시 읽는다 — 직전 세션 이후 바뀌었을 수 있다. 어느 위치의 용어사전을 사용하는지 사용자에게 알린다.
3. **없으면 생성을 제안한다.** 용어사전 없이 여러 문서를 작업하면 같은 용어가 문서마다 다르게 번역된다. 다음을 안내한다:
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/skills/korean-docs/scripts/l10n.mjs" check --init   # .claude/GLOSSARY.md 생성
   ```
   사용자가 원하지 않으면 기본 용어사전만으로 진행하되, 작업 중 용어 결정이 쌓이면(3개 이상) 결정 목록과 함께 다시 제안한다.
4. **기본 용어사전(`GLOSSARY.base.md`)의 규칙도 함께 적용된다.** 프로젝트 규칙이 기본 규칙과 충돌하면 프로젝트 규칙이 우선한다(아래 "기본 규칙 커스터마이징").
5. **`.claude/l10n.json`이 있는지 함께 확인한다.** 없으면 `rules` · `audit` · `suspects`가 꺼진 채로 작업하게 되고, `check`의 0건을 전체 통과로 읽게 된다. 화면 문구·메시지 번들·매뉴얼처럼 언어별 짝이 있는 파일을 가진 프로젝트라면 **용어사전보다 먼저** 만든다: `node "$T" check --init-l10n`. 선언한 뒤 `list`로 파일이 실제로 잡히는지 눈으로 대조한다 — glob이 빗나가면 오류가 아니라 빈 목록이 나온다.

## 작업 워크플로

**작성** — 용어사전의 대역표·문체 규칙을 따라 쓴다. 새 개념어의 표기를 정했다면 즉시 등재한다. 완료 후 감사 스크립트로 확인한다.

**번역** — 원문을 읽고 개념을 이해한 뒤 옮긴다. 도메인 개념이 불확실하면 관련 원문·공식 문서에서 확인하고, 추측으로 번역하지 않는다. 대역표에 없는 용어를 번역했다면 즉시 등재한다. "보존 대상"(아래)을 지킨다. 번역 프로젝트는 감사에 `--untranslated`를 붙여 영문 잔존도 확인한다.

**교정·검수** — 감사 스크립트를 먼저 실행해 기계 검사 가능한 위반을 잡고, `references/korean-style.md` 기준으로 감사가 못 잡는 것(의미 오류, 새로운 번역투, 어순, 조사 오류)을 직접 확인한다. 번역문 검수는 원문 대조로 한다. **교정 중 표현을 교체한 것도 용어 결정이다** — 새 표기를 대역표에, 교체 전 표현을 금지 표기로 등재한다.

**비유·의인화 판정** — 화면 문구든 문서든, 뜻을 흐리는 문장을 찾는 판정은
[references/ui-copy.md](references/ui-copy.md)가 갖는다. 비유, 무생물 주어, 의인화, 표어형 단정,
추상어 압축, 질문형 이름, 업무 은어가 대상이며 **A~W 가운데 넷만 화면 전용이고 나머지는 문서에도
그대로 적용된다.** 화면 문구에는 판정이 하나 더 붙는다 — 「업무용 소프트웨어에서 실제로 쓰는
말인가」. 「무엇에 기대는가」·「보고서가 값을 싣습니다」·「목록은 사람이 손으로 채우지 않습니다」는
셋 다 문법에 맞고 셋 다 화면에 쓰지 않는다.

**전수 검토·수정** — 화면 문구든 문서든 통째로 검토하는 요청(문구 검토 · 카피 검수 · UX 라이팅 ·
문서 전수 교정 · 자연스럽게 고쳐 줘)은 [references/ui-copy-sweep.md](references/ui-copy-sweep.md)의
절차를 따른다 — **검색으로 시작하지 않고 파일을 이름순으로 전부 읽는 것**이 그 첫 항목이고,
**무작위 표본이 0을 낼 때까지 되풀이하는 것**이 마지막 항목이다.

공통 마무리:

```bash
node "${CLAUDE_PLUGIN_ROOT}/skills/korean-docs/scripts/l10n.mjs" check <작업한 파일...>
```

오류 0건까지 수정한다. 경고는 하나씩 검토해 수정하거나 유지 근거를 확인한다. 다국어 자원
파일(i18n·메시지 번들·메일 템플릿)을 고친 작업이면 `audit`도 함께 돌린다 — 같은 규칙을 읽으므로
등재한 용어가 문서와 화면 문구 양쪽에서 걸린다.

## 용어사전 진화 (쓸수록 좋아진다)

용어사전은 완성품이 아니라 작업하면서 자라는 표준이다. 다음 중 하나면 **작업 중 즉시** 프로젝트 용어사전에 등재한다:

- 프로젝트 도메인 개념어 (다른 문서에도 나올 것이 확실한 용어)
- 번역 선택지가 갈리는 용어 (음차 vs 번역, 자연스러운 후보가 둘 이상)
- 이번 작업에서 잘못 쓸 뻔했던 표현 (금지 표기·금지 표현으로 기록)
- **사용자가 교정한 표현** — 대역표에 표준으로, 이전 표현을 금지 표기로 등재한다. **다만 등재는 마지막 단계이지 대응 전체가 아니다** — 낱말 하나를 막는 것으로 끝내면 같은 계열이 다음 주에 다른 활용형으로 돌아온다. 아래 「지적받은 어투는 지침을 진단한다」를 먼저 거친다.

등재 시 `금지 표기` 열에 예상되는 오표기·경쟁 표기를 함께 적는다 — 감사는 이 열로 이루어진다. 등재 후 `--list-rules` 출력에서 방금 등재한 행이 의도한 패턴·수준으로 나오는지 직접 대조한다. 스크립트는 잘못된 정규식·수준 표기·열 밀림(셀 안 `|`)만 알려주므로, 그 외 형식 문제는 출력 대조로만 잡힌다.

**표준 번역을 변경하거나 금지 표기를 추가했다면 같은 세션에서 전수 재감사한다.** 감사 대상 전체를 검사하고(`--all` 또는 audit.paths), 구표기는 `grep -rn`으로도 확인해 일괄 수정한다. 용어사전과 문서가 어긋난 채로 세션을 끝내지 않는다.

### 불확실한 결정 — 임의로 정하지 않고 사용자에게 묻는다

**이 절은 용어 결정에만 적용된다.** 무엇을 고칠지, 몇 개를 고칠지, 규칙을 넓힐지, 검사를 새로
걸지는 여기 해당하지 않는다 — 그 판단은 묻지 않고 한다(아래 「감사는 한 번에 끝난다」).

용어 결정이 다음 중 하나에 해당하면 **혼자 확정하지 않는다**. 임의로 정해 등재하면 잘못된 표준이 조용히 굳고, 나중에 문서 전체를 교체해야 한다.

- 후보가 둘 이상이고 어느 쪽도 명백한 정착어가 아니다 (음차 vs 번역, "부작용" vs "부수 효과" 같은 갈림)
- 도메인 관례를 확신할 수 없다 (팀·업계에서 실제로 쓰는 표기를 모른다)
- **이미 등재된 표준 번역을 변경·교체**하려 한다

처리 절차:

1. 작업 중 발견한 불확실한 결정은 모아 둔다. 산출물에는 추천 표기를 잠정 적용해 작업을 계속한다.
2. **산출물을 확정하기 전에 한 번에 묻는다** — 대화형 세션이면 AskUserQuestion(가능한 환경) 또는 직접 질문으로, 항목마다 후보·추천안·근거를 제시한다.
3. 사용자 응답을 받을 수 없는 실행 환경(백그라운드·서브에이전트)이면 추천안으로 진행하되, 최종 보고의 용어 결정 절에 후보·근거와 함께 확인 요청으로 올린다.
4. 받은 결정은 즉시 등재하고, 탈락한 후보를 금지 표기로 적는다. 잠정 표기와 다르면 산출물도 함께 고친다.

### 완료 보고에 반드시 넣는 것 — 용어 결정 절

문서 작업의 완료 보고에는 **용어 결정 절을 반드시 포함**한다:

1. **등재한 용어** — 영어 → 한국어, 금지 표기 (표 또는 목록)
2. **사용자 확인 대기 항목** — 불확실한 결정의 후보·추천·근거 (위 절차 3에 해당할 때)
3. 등재할 결정이 하나도 없었으면 **"용어 결정 없음"이라고 명시**한다

이 절을 쓸 수 없다면 용어 결정을 추적하지 않은 것이다 — 작업한 파일을 다시 보고 대역표에 없는 용어·교체한 표현을 확인한 뒤 보고한다.

## 지적받은 어투는 지침을 진단한다 — 낱말을 막는 것으로 끝내지 않는다

**사용자가 문장을 짚으면 그 문장은 증상이고 진단 대상은 이 스킬과 프로젝트 지침이다.** 낱말을 금지
표기로 올리는 것은 증상을 덮고 원인을 그대로 두는 일이며, **눈에 보이는 산출물이 나오기 때문에 고친
것처럼 읽힌다.**

**바꾸기 전에 세 가지를 확인한다.**

1. **어느 규칙이 잡았어야 했는데 왜 못 잡았나** — 계열이 필요한 자리에 활용형을 열거했거나, 앵커를
   한 꼴에만 걸었거나, 오탐을 피하려고 좁히다가 나머지를 함께 잃었다. 그렇다면 계열로 넓힌다.
2. **지침 자신이 그 꼴을 허락하고 있지 않나** — 대체 열이 같은 버릇을 저지르고 있거나, 예문이 금지한
   문체로 쓰였거나, 설명 산문 자체가 그 짓을 하고 있는 경우다. **지침을 지침 자신으로 먼저 검사한다**
   — 실제로 대체 열 일곱 자리가 그 자체로 비유였고, 카드가 자기가 막는 표현을 제목에 쓰고 있었다.
3. **계열이 아예 없나** — 그러면 부주의가 아니라 빠진 규칙이다. 계열을 이름 짓고, 정상적인 쓰임과
   가르는 판정법을 함께 적어 등재한다.

**그다음에 원인을 고친다** — 규칙을 계열로 넓히거나, 지침의 그 문장을 다시 쓰거나, 판정법과 함께 계열을
더한다. 낱말 등재는 그 뒤에 오고, 보고에는 **셋 중 무엇이었는지**를 적는다.

## 감사는 한 번에 끝난다 — 검출과 수정 사이에서 멈추지 않는다

**「감사해 줘」는 「찾아서 고쳐 줘」다.** 검출 목록을 내밀고 「고칠까요」로 턴을 끝내는 것은 절반만
한 것이고, 사용자가 받은 것은 그가 시킨 일이 아니라 할 일 목록이다. **찾은 자리는 그 자리에서
고치고, 고친 뒤에 보고한다.**

**다음은 멈출 이유가 아니다.** 하나라도 이유로 삼았다면 그 판단이 틀린 것이다.

| 멈추고 싶어지는 자리 | 실제 |
| --- | --- |
| 검출이 수백 건이다 | 양은 허락을 요구하지 않는다. 계열로 묶어 한 번에 고친다. |
| 파일이 수백 개다 | 같다. 파일 수는 작업의 크기이지 결정 사항이 아니다. |
| 계열이 넓어 판단이 갈린다 | 판단은 이 스킬이 갖는다. 갈리면 기준으로 갈라 고치고, 무엇을 남겼는지 근거와 함께 보고한다. |
| 새 규칙을 등재해야 한다 | 찾은 계열을 규칙·렌즈에 올리는 것은 같은 작업의 일부다. 등재하고 저장소 전체에 다시 돌린다. |
| 규칙을 넓히거나 검사를 새로 걸어야 한다 | 같다. 사람이 손으로 찾은 것은 다음에 또 손으로 찾게 되므로 그 자리에서 기계에 넘긴다. |
| 스킬 저장소를 고쳐야 한다 | 스킬은 사용자의 것이고 그 편집이 작업의 일부다. 무엇을 어느 파일에 넣었는지 보고에 적는다. |
| 계획을 세우고 승인을 받는 편이 안전하다 | 감사에 계획 단계는 없다. 세 가지 개선안을 늘어놓고 고르게 하지 말고 셋 다 한다. |

**멈추는 자리는 둘뿐이다.**

1. **갈리는 용어 결정** — 그것도 즉시 묻지 않는다. 추천 표기를 잠정 적용해 **끝까지 진행한 뒤**
   모아서 한 번 묻는다(위 「불확실한 결정」).
2. **git 커밋·푸시** — 전역 지침이 사용자 요청 때만 하도록 정한다. 감사 자체는 커밋과 무관하게
   끝까지 간다.

**유혹은 「양이 많으니 확인받는 것이 공손하다」이다.** 목록을 보이는 것이 배려로 느껴지지만, 감사를
시킨 사람이 원한 산출물은 목록이 아니라 고쳐진 파일이다. 또 하나는 **「규칙을 새로 만드는 건 다른
일이다」**인데, 찾은 계열을 기계에 넘기지 않으면 다음 사람이 같은 것을 다시 손으로 찾는다.

**「진행할까요」·「어느 쪽으로 할까요」·「판단해 주세요」로 턴을 끝내지 않는다.** 판단이 필요하면
판단하고, 그 판단과 근거를 완료 보고에 적는다. 사용자는 보고를 읽고 되돌릴 수 있다.

### 재감사 (사용자 요청 시)

사용자가 "용어사전으로 다시 검사해줘", "전체 재감사" 등을 요청하면:

1. 용어사전을 다시 읽는다 (바뀌었을 수 있다).
2. **네 명령을 다 돌린다** — `check` · `audit` · `rules` · `suspects`. 하나만 돌고 0건을 통과로
   읽지 않는다.
3. **검사가 실제로 도달하는지 확인한다** — 일부러 위반을 한 줄 넣어 걸리는지 보고 지운다. 0건과
   「닿지 못함」은 화면에서 구별되지 않는다.
4. 오류를 전부 수정한다. 경고는 하나씩 판정해 고치거나 유지 근거를 적는다.
5. `suspects`와 렌즈로 기계가 못 잡는 자리를 읽고, 찾은 계열은 규칙·렌즈에 올린 뒤 다시 돌린다.
6. 오류 0건을 확인한 뒤 결과(파일 수, 수정 건수, 유지한 경고와 근거, 등재한 규칙)를 보고한다.

**2~5는 한 턴 안에서 이어진다.** 사이에서 사용자에게 되묻지 않는다.

## 감사 도구 — 도구는 하나, 규칙 원천은 둘

`scripts/l10n.mjs` 하나가 문서와 다국어 자원을 같은 규칙으로 검사한다. 용어사전(기본 + 프로젝트
병합)이 `check`와 `audit`의 금지 표기를 대고, 규칙 팩(`RULES.base.json` + 프로젝트
`.claude/l10n-rules.json`)이 `rules` 훑기를 댄다. **용어사전에 등재하면 문서(.md·.svg)와 화면
문구(i18n·메시지 번들·메일·보드 소스)가 함께 걸린다** — 낱말 금지는 용어사전에, 문장 패턴
정규식은 hit/miss 예문과 함께 규칙 팩에 등재한다.

```bash
T="${CLAUDE_PLUGIN_ROOT}/skills/korean-docs/scripts/l10n.mjs"
node "$T" check [경로...]        # 문서 감사 — audit.paths 대상, 없으면 프로젝트 전체 (훅과 같은 판정)
  --all             # 프로젝트 전체 (audit.paths 무시)
  --strict          # 경고도 실패 처리
  --untranslated    # 영문 문장 잔존 경고 (번역 프로젝트)
  --glossary <p>    # 용어사전 경로 직접 지정 (탐색 생략)
  --no-base         # 기본 용어사전 제외
  --list-rules      # 병합된 규칙 확인 (용어사전 수정 후 등재 결과 대조)
  --init            # .claude/GLOSSARY.md 템플릿 생성
node "$T" audit [--kind K]       # 자원 감사 — 번역 누락 · 금지 표기 · 조사 · 짝 언어 파일
node "$T" rules --test           # 규칙 팩이 제 예문(hit/miss)을 통과하는지 검증
node "$T" rules [--scope S]      # 문장 규칙으로 자원을 훑는다 (고치지 않는다)
node "$T" suspects [--json]      # 문체가 어색한 문장을 점수순으로 뽑는다
node "$T" grep <패턴> [--regex]  # 자원의 문구 값에서 찾는다
node "$T" apply --patch <파일>   # 다시 쓴 문장 목록을 반영한다 (--write 전까지 미리보기)
```

`scripts/check-glossary.mjs`는 같은 문서 감사 엔진의 훅 진입점이라 `check`와 판정이 같다.

### 용어사전이냐 규칙 팩이냐 — 활용하는지로 가른다

**금지할 것이 활용하는 용언이면 규칙 팩, 활용하지 않는 것이면 용어사전이다.**

용어사전 행은 hit/miss 예문을 달 수 없고 예외도 적을 수 없다. 그래서 활용형이 있는 말을 거기
넣으면 **적어 둔 한 꼴만 잡히고 나머지가 통째로 빠져나간다** — 용어사전에 `가지고 있`만 있었던 탓에
「갖는다·가진다」가 그대로 지나갔고, 결국 `inanimate-have`가 규칙으로 따로 태어났다. 그 규칙은
「사람이 주어인 것은 정상」이라는 예외까지 적어야 했는데, 그것도 용어사전 행으로는 못 쓴다.

| 넣을 것 | 자리 |
| --- | --- |
| 표기·음차·오탈자 (`라이센스` · `디렉토리` · `텀`) | 용어사전 |
| 이 프로젝트가 정한 대역어와 금지 표기 | 프로젝트 용어사전 |
| 활용하는 용언 (갖는다 · 붙인다 · 부딪힌다) | 규칙 팩 |
| 예외를 적어야 하는 것 (「사람이 주어면 정상」) | 규칙 팩 |

**어디에 넣든 검사가 닿는 파일은 같다** — 선언이 없으면 `rules`도 `check`와 같은 문서 집합을
읽으므로, 이 판단은 커버리지 문제가 아니라 순전히 「기계가 정확히 판정할 수 있는가」의 문제다.

**훅은 플러그인이 제공한다 — 프로젝트가 따로 걸지 않는다.** `hooks/hooks.json`이 `Write|Edit|MultiEdit`에
`hooks/check-md-glossary.mjs`를 걸어 두었고, 그 선언이 이 스크립트를 실행한다. **차단 훅이라 오류가 있으면
편집이 되돌려지는 것이 아니라 그 자리에서 멈춰 세운다.**

**돌지 않는 조건은 프로젝트 용어사전이 없는 것 하나다** — 훅은 `.claude/GLOSSARY.md`(또는 루트
`GLOSSARY.md`)가 있는 프로젝트에서만 검사하고, 없으면 조용하다. 그래서 용어사전이 없다는 것은
「규칙이 적다」가 아니라 **쓰기 시점 검사가 통째로 꺼져 있다**는 뜻이다.

**훅이 도는지 의심스러우면 확인하지 말고 시험한다.** 설정 파일을 뒤지는 것으로는 알 수 없다 —
전역 `settings.json`에도 프로젝트 `.claude/settings.json`에도 선언이 없는 것이 정상이고, 플러그인의
`hooks/hooks.json`에 있다. **금지 표기를 일부러 한 줄 넣고 저장해 보는 것이 유일하게 확실한
확인이며**, 그 방법으로 확인한 뒤에는 넣은 줄을 반드시 지운다.

**자원 감사에는 프로젝트 선언이 필요하다.** 어느 경로가 다국어 자원인지는 프로젝트의
`.claude/l10n.json`이 `kinds`(경로 glob · 형식 · 언어 · `register`)로 선언한다 — 스킬은 기본 배치를
갖지 않는다(프로젝트마다 다른 배치를 공용 코드에 박으면 다른 프로젝트에서 조용히 틀린다).
`register`는 그 부류의 문체를 말한다: `"screen"`(화면 문구, 합니다체) · `"manual"`(독자용
합니다체 산문) · 생략(-다체 작업 문서). `format`은 `json` · `properties` · `ts`(`'키': '문구'`
객체 리터럴로 쓴 카탈로그) · `markdown` · `html` · `wireframe` · `text` · `auto`다.

**파일 이름까지 번역하는 부류는 `stemKey`로 짝을 맞춘다.** 짝 언어 검사는 경로에서 언어 마디만
빼고 남는 것으로 두 언어를 잇는데, `01-시작하기.md`와 `01-getting-started.md`처럼 이름이 함께
번역되면 이을 것이 남지 않아 **모든 쪽이 「짝 없음」으로 뜬다.** 번역되지 않는 자리(단계 번호,
아이디)를 잡는 정규식을 적으면 그 갈무리가 짝의 열쇠가 된다 —
`"stemKey": "^docs/manual/[^/]+/(\\d+)-"`. 정규식이 빗나간 파일은 제 경로를 그대로 쓰므로
목록에서 사라지지 않고 짝 없는 것으로 남는다.

**선언이 없어도 문장 검사는 돈다.** `rules` · `suspects` · `grep` · `list`는 `kinds`가
없으면 `check`가 읽는 문서 집합(`.md` · `.mdx` · `.svg`)으로 떨어진다. 한 저장소가 「어느
파일을 검사하는가」에 두 답을 내지 않게 하려는 것이며, 문서만 있는 프로젝트가 낱말 검사
하나만 돌고 「오류 0건」을 통과로 읽던 자리를 없앤다.

**`audit`만은 선언을 요구한다** — 짝 언어를 대조하는 명령이라 문서 집합에는 댈 짝이 없다.
화면 문구·메시지 번들처럼 언어별 짝이 있는 파일을 가진 프로젝트는 선언을 만든다.

```bash
node "$T" check --init-l10n   # .claude/l10n.json + .claude/l10n-rules.json 뼈대
```

**glob 함정**: `git ls-files`의 `**`는 경로 마디 **하나 이상**이라 `locales/**/ko.json`은
`locales/ko.json`에 걸리지 않는다. 두 모양이 다 있는 부류는 glob을 둘 적는다 — 빠뜨린 파일은
오류가 아니라 **침묵**으로 나타나고, 그 침묵이 「문제 없음」으로 읽힌다.

**추적하지 않는 파일도 같은 침묵을 낸다.** 열거가 `git ls-files`로 이루어지므로 **아직
`git add` 하지 않은 파일은 목록에 없고, 검사되지 않은 채 0건으로 보고된다.** 방금 쓴 파일이
가장 검사가 필요한데 바로 그 파일이 빠지고, 결과 화면은 통과와 구별되지 않는다 — 새로 쓴 화면
파일 16개가 `rules` 0건을 받고, 스테이징하자마자 10건이 나온 적이 있다. **감사 전에 새
파일을 스테이징한다.** 의심스러우면 `list`가 세는 파일 수를 실제 파일 수와 눈으로 대조한다.

### 규칙이 0건이라는 것은 「깨끗하다」가 아니다

**규칙은 등재된 꼴만 본다.** 한국어는 같은 비유를 무한한 꼴로 쓰므로, 규칙을 아무리 늘려도 사람이
읽어야 찾는 것이 남는다. 실제로 규칙 일흔둘이 0건을 낸 보드를 파일명 순서로 읽었더니 한 구역에서만
열넷이 나왔고, **그 열넷 가운데 규칙에 걸린 것은 하나도 없었다.**

| 규칙에 든 꼴 | 규칙이 놓친 같은 계열 |
| --- | --- |
| 결재가 **올라갑니다** | 알림이 **갑니다** · 서버로 **간다** · 다음 수단으로 **넘어갔습니다** |
| **심사를** 연다 | **플라이아웃이** 연다 |

세 가지가 겹쳐서 그렇게 된다.

1. **목적어를 열거할 수밖에 없다.** 「파일을 연다」·「창을 연다」가 정상이라 어간 「연다」로 넓힐 수
   없고, 그래서 심사·회차·기한을 적는다. 목적어는 제품마다 새로 생긴다.
2. **활용형이 음절을 통째로 바꾼다.** 「넘어갑니다」를 넣어도 「넘어갔습니다」·「넘어갈」·
   「넘어가지 않습니다」는 다른 글자다.
3. **같은 비유가 다른 동사로 나타난다.** 가다·오다·넘어가다·올라가다·흐르다가 한 계열인데, 정상
   쓰임이 많아 어간으로 막을 수 없다.

**셋 다 정상 쓰임 때문에 좁힌 결과이지 규칙의 결함이 아니다.** 좁히면 새는 것이 규칙의 성질이다.
사람은 「플라이아웃**이** 연다」에서 주어가 사물임을 한 번에 보지만 정규식은 주어를 볼 수 없다.

그래서 **규칙 0건을 받은 뒤에도 references/ui-copy-sweep.md의 순차 읽기를 건너뛰지 않는다.**
규칙은 사람이 읽을 것을 줄여 주는 바닥이지, 읽기를 대신하는 천장이 아니다.

**읽기를 감당할 양으로 줄이는 도구가 렌즈다**([references/reading-lens.md](references/reading-lens.md)).
규칙과 정반대로 넓게 짜서 사람이 읽을 후보를 뽑는다 — 오탐이 비용이 아니라 읽을 거리이므로 넓어도
되고, 넓어야 새지 않는다.

```bash
K="$HOME/.claude/skills/simplecore/skills/korean-docs"
node "$K/scripts/l10n.mjs" grep --regex "$(cat "$K/references/lens.txt")"
```

화면 문구 27,830개가 1,336개로 줄어든다. **`rules`가 0건이어도 이것은 0건이 아니다.**

**이 도구는 찾기만 한다 — 일괄 치환 명령은 없고 만들지 않는다.** 규칙은 낱말이 어디 있는지 알
뿐 그 자리에서 무엇을 가리키는지 모른다. 각자 옳게 걸린 두 규칙이 한 문장을 「라이선스 수량
라이선스 하나가」로 만든 사고가 치환을 없앤 이유다. 고칠 자리를 `check`·`audit`·`rules`·
`suspects`로 뽑고, 문맥을 읽고 다시 쓴 문장을 `apply --patch`로 되돌려 넣는다 — 저장된 원문이
파일과 어긋나면 반영을 거절한다.

- 기본 감사 대상·제외 패턴·다국어 자원 경로·영문 잔존 검사 여부는 프로젝트 용어사전의 front matter(`audit.paths`, `audit.exclude`, `audit.localeResources`, `audit.untranslated`)로 설정한다.
- **명시적으로 지정한 파일은 `audit.exclude`를 무시하고 항상 검사한다** — 제외 패턴은 디렉터리 지정과 스캔에만 적용된다. 용어사전 파일 자체는 검사하지 않는다(금지 표기가 정의상 들어 있다).
- 코드 블록·인라인 코드·링크 경로·URL은 검사에서 제외되므로 코드 예제는 오탐을 만들지 않는다.
- **용어사전과 무관하게 항상 도는 검사가 둘 있다.** 조사 어긋남(이/가·을/를·과/와를 앞 글자 받침에 맞췄는지, 오류)과 같은 말이 잇달아 나오는 것(경고). 둘 다 일괄 치환이 남기는 자국이라, 용어를 바꾼 뒤에는 이 둘이 특히 잘 걸린다. 은/는은 관형형 어미(있는·없는)와 겹쳐 검사하지 않는다.
  - **조사 검사는 규칙이 써 넣을 수 있는 낱말 뒤에서만 판정한다.** 한국어 아무 낱말이나 보는 것이 아니라, 용어사전과 규칙 팩의 대체어로 등장할 수 있는 낱말(「화면」·「항목」·「아이디」…) 뒤의 조사만 본다 — 달리 하면 「경로가」·「초과를」처럼 사람이 일부러 쓴 것과 치환이 망가뜨린 것을 가릴 수 없다. **그래서 「값를」은 걸리지 않는다.** 등재되지 않은 낱말 뒤의 조사는 사람이 읽어야 하고, 그 자리는 references/ui-copy.md의 L절이 맡는다.
  - **중복 검사는 낱말이 맞붙은 꼴만 본다**(`같은 같은`). 「기록 기록을」처럼 뒤엣것에 조사가 붙으면 같은 낱말이 아니므로 걸리지 않는다.
- 표 형식(열 구성, `/pattern/` 정규식, `,` 구분, 셀 내 `|` 금지, 정규식 내 `,` 금지)을 지켜야 파싱된다.

## SVG 다이어그램 텍스트

SVG 파일의 `<text>`·`<tspan>` 내용은 렌더된 한국어 산출물이다 — 문서와 똑같은 표기·용어·번역투 기준을 적용한다. 문서를 작성·번역·교정·감사할 때 범위 안의 SVG를 함께 손본다. 문서에 삽입된 SVG뿐 아니라 **저장소에 독립으로 있는 외부 `.svg` 파일도 대상**이다. 다이어그램 라벨이 고친 본문과 어긋나면 그 자체가 불일치다.

- **감사 대상.** 감사 스크립트가 `.svg`를 검사한다 — `<text>`/`<tspan>` 본문만 보고 태그·속성·스타일·경로 데이터는 무시하므로 좌표·색·`id`에서 오탐하지 않는다. 프로젝트 전체 스캔·디렉터리 지정에 SVG가 포함되고, 파일을 직접 지정해도 검사한다. 감사 훅도 SVG 쓰기에 발동한다. 특정 SVG를 빼려면 `audit.exclude`에 넣는다.
- **mermaid 코드 블록과 구분한다.** 문서 안 다이어그램 **코드 블록**(mermaid 등)은 노드 ID·내장 문법과 섞여 있어 통째로 원문 유지한다(보존 대상). 반면 렌더돼 저장된 `.svg` 파일의 보이는 라벨은 완성된 산출물이라 기준을 적용한다.
- **텍스트를 고치면 레이아웃을 다시 검증한다.** 라벨의 글자가 바뀌면 글자폭이 달라져 박스를 넘치거나 잘릴 수 있다. SVG 텍스트를 수정한 뒤에는 `svg-diagrams` 스킬로 다시 렌더·감사한다(`audit.py lint`·render). 텍스트만 치환하고 레이아웃을 확인하지 않으면 잘린 그림이 남는다.

## 다국어 자원 파일의 문구

다국어(i18n)를 쓰는 프로젝트에서 **화면에 실제로 나가는 한국어는 전부 로케일 자원 파일에 있다**(`packages/i18n/src/resources/ko.ts`, `locales/ko.json` 등). 문서보다 훨씬 많은 사람이 읽는 문구이므로 표기·용어·번역투 기준을 똑같이 적용하고, 그 위에 **화면 문구 기준([references/ui-copy.md](references/ui-copy.md))을 더한다.** 문구를 새로 넣거나 고칠 때 그 자원 파일을 감사 범위에 포함한다.

- **프로젝트가 경로를 직접 선언한다.** 자원 파일의 위치와 이름은 프로젝트마다 다르므로 스크립트가 추측하지 않는다. 프로젝트 용어사전 front matter의 `audit.localeResources`에 glob을 적어야 감사 대상이 된다. 선언하지 않은 프로젝트는 아무 영향도 받지 않는다.
- **감사 대상.** 선언한 파일은 **따옴표 문자열의 값**만 보고 나머지는 무시한다 — 객체 키(`'readers.list.title'`)와 주석은 화면 문구가 아니므로 검사하지 않는다. `.ts`·`.js`·`.json`·`.jsonc`에서 동작하고, 확장자와 무관하게 프로젝트 전체 스캔·디렉터리 지정에 포함되며 파일을 직접 지정해도 같은 방식으로 검사한다.
- **영문 잔존 검사(`--untranslated`)는 적용하지 않는다.** 영어 로케일 파일은 정의상 영문이다.
- 특정 자원 파일을 빼려면 `audit.exclude`에 넣는다.

## 기본 규칙 커스터마이징

기본 용어사전이 프로젝트·도메인과 맞지 않을 때, 기본 파일을 고치지 말고 프로젝트 용어사전에서 조정한다:

- **대체**: 같은 `영어` 키(또는 같은 `금지` 패턴)의 행을 프로젝트 용어사전에 정의하면 기본 행 **전체**가 교체된다. 기본 행의 금지 표기 검사를 유지하려면 프로젝트 행에 함께 옮겨 적는다. 새 오표기만 보태려면 행 재정의 대신 `## 금지 표현`에 별도 행으로 추가하는 편이 안전하다.
- **비활성화**: `## 기본 규칙 예외` 표에 영어 키(행 전체) 또는 패턴 텍스트(개별 규칙)를 적는다. 예: 금융 문서의 `레버리지`, 메시징 문서의 `소비`.

`GLOSSARY.base.md` 자체는 수정하지 않는다 — 모든 프로젝트에 공유되는 파일이라 한 프로젝트의 사정을 넣으면 다른 프로젝트에서 틀린 결과를 낸다.

## 보존 대상 (번역·교정 시 건드리지 않는 것)

- 코드 블록·인라인 코드·설정 키·CLI 명령·SQL 키워드·파일 경로·URL. 코드 블록 안 주석도 원문 유지.
- front matter의 키와 슬러그 값(`id`, `slug` 등). `title`·`description` **값**은 번역한다.
- 링크 경로·앵커·이미지 경로. 링크 **텍스트**는 번역한다.
- 마크다운 구조(제목 수준, MDX import/export 문, 컴포넌트 이름·속성, HTML 태그).
- 제목 자동 생성 앵커를 쓰는 사이트(Docusaurus 등)에서는 번역한 제목(h2~h6)에 원문 앵커를 명시한다: `## 버전 저장 {#version-storage}`. 앵커가 바뀌면 들어오는 링크가 깨진다.
- 다이어그램 **코드 블록**(mermaid 등)은 라벨까지 통째로 원문 유지 — 노드 ID·내장 코드와 섞여 있어 부분 번역 시 렌더링이 깨진다. 단, 렌더돼 저장된 외부 `.svg` 파일의 `<text>` 라벨은 보존 대상이 아니라 감사·수정 대상이다 (아래 "SVG 다이어그램 텍스트").
- 제품명·언어명·약어(프로젝트 용어사전의 "원문 유지 용어" 표).

## 전역 지침 연결 — 없으면 먼저 제안한다

이 스킬은 문서 작업뿐 아니라 **모든 한국어 답변**을 지배한다. 그런데 description 트리거는 "문서를 써 줘" 같은 요청에만 확실히 걸리고, 평범한 질문에는 걸리지 않는다. 그 간극을 메우는 것은 전역 `~/.claude/CLAUDE.md`의 한 문단뿐이다.

**로드 시 한 번 확인하고, 없으면 제안한다.** 사용자는 이 연결이 필요하다는 사실을 알 이유가 없다.

```bash
node "${CLAUDE_PLUGIN_ROOT}/scripts/detect-simplecore.mjs" --json   # globalKorean.present 를 읽는다
```

`globalKorean.present`가 false면, 한 문장으로 무엇이 빠졌고 그 문단이 무엇을 막아 주는지 말하고 `/simplecore:init`을 제안한다. 세션당 한 번만 제안하고, 거절하면 그대로 진행하며 다시 꺼내지 않는다. 직접 쓰겠다는 경우 넣을 문단은 다음이다:

> 세션에서 한국어 답변·산출물을 처음 작성하기 전에 `simplecore:korean-docs` 스킬의 `references/response-style.md`를 반드시 읽고 세션 내내 적용한다.

프로젝트 용어사전이 없을 때도 같다 — 없으면 감사 훅이 침묵하고 용어가 문서마다 갈린다. 시작 절차 3의 `--init`을 제안한다.

## Red Flags — 이 생각이 들면 멈춘다

- 새 용어를 "일단 이렇게 옮기고 나중에 정리"하려 한다
- 감사 오류를 고치는 대신 규칙을 완화하려 한다 (완화가 정당하면 먼저 사용자에게 근거를 보고)
- 사용자가 교정해 준 표현을 용어사전에 등재하지 않고 넘어가려 한다
