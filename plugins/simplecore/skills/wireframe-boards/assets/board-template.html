HOW TO READ THIS BOARD — REQUIRED BEFORE IMPLEMENTING

  1. This is a low-fidelity wireframe, not a design. It fixes what is on each screen, in which state, and how the user moves between screens — the minimum needed to start building. It says nothing about how the product should look.
  2. Never reproduce this board's appearance. Greyscale fills, 1px borders, corner radii, paddings, the single accent color, device chrome, and this monospaced notation are board notation. Build with the project's own design system and component library, and let it decide color, type, spacing, elevation, and motion.
  3. Grey bars and boxes are placeholders (.bar, .img-ph, .qr-ph, .thumb) standing in for real data. They are not grey rectangles in the product.
  4. Real text is the specified wording — keep it. Button labels, screen titles, field labels, tab names, empty-state and error copy are the intended strings. Placeholder bars are not strings.
  5. Every frame is one screen × one state. States drawn here (empty, error, loading, expired, terminal, permission-gated, overlay) are requirements; implement all of them, not only the happy path.
  6. The frame label reads route — screen — state. Notes carry AUTH: (entry precondition), DATA: (source endpoint), OPEN: (unresolved question).
  7. An OPEN: note blocks that part of the implementation. Resolve it with the board's author — never guess, and never let the drawn shape stand in for the missing decision.
  8. Device frames are reference viewports, not breakpoints to hard-code. Phone and tablet frames are fixed device viewports. Desktop frames pin only the width: the page height is fluid, and the dashed fold line marks the smallest supported window — everything the user must act on belongs above it.
  9. A narrow/wide pair is one responsive screen, not two screens. The pair records how the layout reflows between the two viewports; implement a single screen that spans them.
  10. Arrows, numbered steps, stickies, and fold lines are annotations describing navigation and intent. Never render them as UI.
  11. Visual detail is deliberately unspecified; screens and states are not. A screen or state missing from this board has not been specified — ask, do not invent. Where this board and the project's frontend conventions disagree about structure or components, the project's conventions win.
